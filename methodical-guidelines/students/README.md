## О дисциплине

### Цель обучения

Сформировать системное понимание работы с большими данными и развить навыки проектирования, создания и развития надёжных, масштабируемых и эффективных решений в области инженерии данных.

### Планируемые результаты

По завершении дисциплины вы сможете:

| № | Результат обучения |
|---|-------------------|
| 1 | Анализировать требования к хранению, интеграции и обработке больших данных |
| 2 | Выбирать модель хранения и технологический стек с учётом структуры данных, нагрузки и требований к надёжности |
| 3 | Проектировать архитектуру хранилища данных и многомерные модели для аналитических задач |
| 4 | Создавать процессы сбора, очистки, преобразования и загрузки данных из разнородных источников |
| 5 | Развёртывать и использовать распределённые инструменты хранения и обработки данных |
| 6 | Реализовывать пакетные и потоковые конвейеры обработки данных |
| 7 | Настраивать оркестрацию, мониторинг, контроль качества и прослеживаемость происхождения данных |
| 8 | Оценивать производительность, масштабируемость, отказоустойчивость и качество решений |
| 9 | Разрабатывать и защищать командный прототип инфраструктуры сбора, хранения и обработки больших данных |

### Пререквизиты

Для успешного освоения дисциплины необходимы знания и навыки из курсов:

- «Базы данных» — реляционная модель, SQL, проектирование схем;
- «Методы искусственного интеллекта» — основы машинного обучения;
- «Дискретная математика и математический анализ» — математическая база;
- «Структуры данных и алгоритмы» — алгоритмическая сложность;
- «Операционные системы и сети» — основы распределённых систем;
- «Программирование на языке Python» — написание скриптов и ETL-процессов.

## Структура и содержание модулей

Дисциплина состоит из **четырёх модулей** и **командной проектной работы**:

| № | Модуль | Содержание | Формы контроля |
|---|--------|------------|----------------|
| 1 | **Модели хранения данных** | OLTP vs OLAP, хранилища данных, многомерное моделирование, облачные хранилища | Тестирование, лабораторная работа |
| 2 | **Подготовка данных** | ETL/ELT-процессы, интеграция данных, очистка и консолидация, качество данных | Коллоквиум, тестирование, лабораторная работа |
| 3 | **Технологии и инструменты обработки данных** | Hadoop, Spark, Trino, пакетная и потоковая обработка, оркестрация (Airflow) | Контрольная работа, лабораторные работы |
| 4 | **Технологии организации инфраструктуры больших данных** | Архитектура Big Data, масштабируемость, отказоустойчивость, выбор технологического стека | Тестирование, лабораторная работа |
| 5 | **Командная проектная работа** | Интегральный проект по созданию прототипа инфраструктуры Big Data | Защита проектной работы |

**Промежуточная аттестация:** экзамен по итогам 5 семестра.

## Рекомендации по подготовке к контрольным мероприятиям

### 1. Тестирование

**Формат:** 20 вопросов (15 с одним ответом + 5 с несколькими ответами)  
**Продолжительность:** 45 минут  
**Макс. балл:** 25

**Что проверяется:**
- Понимание архитектуры Big Data и слоёв Data Lake
- Знание технологий: Kafka, Spark, Airflow, Hadoop, ClickHouse, Redis
- Принципы масштабируемости, отказоустойчивости, обработки потоков

**Рекомендации по подготовке:**
1. Изучите лекционные материалы и конспекты по модулю
2. Изучите контнольные материналы и критерии оценивания по [Модулю 1](../../M1-storage-models/kim-01-test.md), [Модулю 2](M2-data-preparation/kim-02-test.md), [Модулю 3](M3-processing-technologies/kim-05-test.md), [Модулю 3](../../M3-processing-technologies/kim-07-test.md), [Модулю 4](../../M4-big-data-infrastructure/kim-01-test.md)
3. Повторите назначения ключевых технологий и их отличия
4. Решите практические кейсы по выбору стека для сценариев

**Запрещено:** Использование документации, поисковых систем, генеративного ИИ, помощи других лиц.

### 2. Лабораторные работы

Предполагаются шесть лабораторных работ:

- [Модуль 4](../../M4-big-data-infrastructure/kim-02-lab-infrastructure.md)

**Продолжительность:** 1–2 недели  
**Макс. балл:** 100

**Что проверяется:**
- Способность выбрать технологический стек для сценария
- Навыки проектирования архитектуры инфраструктуры
- Обоснование решений по масштабируемости и надёжности

**Требования к отчёту:**

4. **Выбор технологий** (сравнение альтернатив, обоснование)
5. **Архитектурная схема** (диаграмма с потоками данных)
6. **План масштабируемости** (оценка ресурсов, стратегия роста)
7. **Надёжность и стоимость** (отказоустойчивость, восстановление)
8. **Выводы** (ключевые решения, компромиссы, улучшения)

**Формат:** Командная разработка прототипа инфраструктуры  
**Срок:** 4–6 недель  
**Защита:** Презентация + демонстрация + ответы на вопросы

**Этапы проекта:**

| Этап | Содержание | Срок |
|------|------------|------|

**Требования к проекту:**

1. **Архитектурное решение** — полная схема инфраструктуры
2. **Реализованный прототип** — работающий код/конфигурации
3. **Документация** — описание решения, инструкции по развёртыванию
4. **Презентация** — 10–12 слайдов с ключевыми решениями
5. **Демонстрация** — показ работы системы в действии

**Распределение ролей в команде:**

| Критерий | Вес |
|----------|-----|

## Порядок выполнения и сдачи работ

### Общие требования

1. **Сроки сдачи** устанавливаются в начале семестра и публикуются в LMS.
2. **Просроченные работы** принимаются со штрафом 10% за каждый день просрочки (максимум 5 дней).
3. **Повторная сдача** возможна после устранения замечаний в течение 2 недель.
4. **Апелляция** подаётся в течение 3 рабочих дней после объявления оценки.

### Формат сдачи лабораторных работ

```
Формат отчёта: PDF или Markdown
Название файла: <Фамилия>_<Группа>_Lab<N>_<Вариант>.pdf
Способ сдачи: LMS / GitHub Repository / Email
```

**Структура репозитория для лабораторной:**

```text
lab-<номер>/
├── README.md              # Описание и инструкции
├── report/                # Отчёт (PDF/MD)
├── src/                   # Исходный код
├── diagrams/              # Диаграммы и схемы
├── docker-compose.yml     # Конфигурация развёртывания
└── tests/                 # Тесты (если применимо)
```

### Защита работ

- **Индивидуальная защита:** 5–10 минут + вопросы
- **Формат:** Очно или онлайн (по согласованию)
- **Вопросы на защите:** Могут касаться любых аспектов выполненной работы

## Использование генеративного ИИ

### Разрешено

| Ситуация | Примеры |
|----------|---------|
| **Генерация шаблонов** | Шаблоны кода, конфигураций, документации |
| **Объяснение концепций** | Пояснение терминов, алгоритмов, архитектурных паттернов |
| **Поиск ошибок** | Анализ сообщений об ошибках, предложения по исправлению |
| **Рефакторинг** | Улучшение читаемости кода, оптимизация запросов |
| **Визуализация** | Генерация диаграмм из текстового описания (PlantUML, Mermaid) |
| **Подготовка к защите** | Генерация вопросов для самопроверки |

### Запрещено

| Ситуация | Причина |
|----------|---------|
| **Полное решение заданий** | Нарушение академической честности |
| **Генерация отчёта без понимания** | Невозможность объяснить решения на защите |
| **Копирование кода без анализа** | Отсутствие навыков отладки и модификации |
| **Прохождение тестирования** | Недопустимо использование любых внешних источников |

### Требования к декларированию

Если вы использовали генеративный ИИ при выполнении работы, **добавьте раздел в отчёт**:

```markdown
## Использование генеративного ИИ

| Инструмент | Цель использования | Доля в работе |
|------------|-------------------|---------------|
| GitHub Copilot | Генерация шаблонов SQL-запросов | ~15% |
| ChatGPT | Пояснение концепции window functions | Консультация |
| PlantUML AI | Генерация начальной версии диаграммы | ~30% |
```

**Важно:** Вы должны быть способны объяснить и аргументировать **любое** решение в работе, даже если оно было сгенерировано ИИ.

## Командная проектная работа

### Формирование команд

- **Размер команды:** 3–5 человек
- **Срок формирования:** 1 неделя семестра
- **Распределение:** Самостоятельно или по назначению преподавателя

### Рекомендации по командной работе

1. **Определите роли** на старте (тимлид, архитектор, разработчик, DevOps, аналитик)
2. **Установите правила коммуникации** (еженедельные встречи, канал в мессенджере)
3. **Используйте систему контроля версий** (Git + GitHub/GitLab)
4. **Ведите журнал решений** (Architecture Decision Records — ADR)
5. **Распределяйте задачи письменно** (Trello, Jira, GitHub Projects)

### Разрешение конфликтов

| Тип конфликта | Рекомендация |
|---------------|--------------|
| **Технический** | Проведите сравнительный анализ альтернатив, привлеките преподавателя |
| **Организационный** | Зафиксируйте ожидания письменно, проведите ретроспективу |
| **Межличностный** | Обсудите открыто, при необходимости обратитесь к преподавателю |

### Вклад участников

Каждый участник должен:
- Выполнить минимум 1 значимый модуль системы
- Внести вклад в документацию
- Участвовать в подготовке презентации
- Быть готовым ответить на вопросы по **всей** архитектуре на защите

### Часто задаваемые вопросы (FAQ)

**В:** Можно ли сдавать работы после дедлайна?  
**О:** Да, с штрафом 10% за каждый день (макс. 5 дней). После — только по уважительной причине.

**В:** Что делать, если команда не может договориться?  
**О:** Проведите встречу с преподавателем для модерации обсуждения.

**В:** Можно ли использовать чужой код из открытых источников?  
**О:** Да, с обязательным указанием источника и адаптацией под задачу.

**В:** Как подготовиться к экзамену?  
**О:** Повторите все модули, прорешайте тесты, изучите примеры билетов в [Exam/](../../Exam/README.md).
